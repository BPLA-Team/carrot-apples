# Домашнее задание по курсу "Кибериммунитет"

## Команда и выбор темы

Команды по ~3 человека


Выбор темы – проектирование сложной технической системы, например БПЛА с определенной функцией, клиент-серверное приложение, высоконагруженная система, система управления технологическим процессом, систему управления критическим инфраструктурным объектом. 
Можно выбирать темы на основании выполняемых вами задач на текущем месте работы при согласовании с руководителем.


В рамках решения мы рассматриваем этапы со стороны условного Заказчика на разработку системы, и этапы с условного Исполнителя разработки.

## Со стороны Заказчика, при участии Исполнителя


### Концепция Безопасности Продукта (КБП)

Здесь мы формулируем текстом задачу нашей системы, внешние по отношению к системе условия и взаимодействия, обеспечивающее ее функционирование. Главное – перечисляем в таблице ценности, с которыми взаимодействует система, негативные события, возникающие при нарушении этих ценностей, оценку ущерба при таком нарушении, в комментариях указываем дополнительную информацию, возможные действия при таких нарушениях.

### Контекст

описываем в виде диаграммы состояний. Как наша система взаимодействует с внешними компонентами, на основании формулировки из предыдущего пункта.

### Базовые сценарии использования системы

описывается в виде диаграммы последовательности, на основании предыдущего пункта. Добавляем комментарии по особенностям взаимодействия. Что мы можем делать с помощью нашей системы.

## Со стороны Исполнителя


### High-Level Architecture (HLA)/Архитектура

Здесь впервые появляется собственная архитектура системы. Описывается в виде диаграммы состояний из компонентов и взаимодействий между ними. Отдельной таблицей описываются компоненты системы с описанием назначения и дополнительными комментариями. Тут мы представляем систему без учета кибериммунного подхода, опираясь лишь на целевую задачу. Какие компоненты нужны для выполнения задач системы?

### Базовые сценарии + HLA

Здесь мы уже подробнее описываем с помощью диаграммы последовательностей упомянутые ранее Базовые сценарии, как они реализуются на базе нашей Архитектуры из предыдущего пункта. Как с помощью данных компонентов выполнить задачи системы?

### Цели и Предположения Безопасности (ЦПБ)

Списком  перечисляем отдельно цели безопасности  и отдельно предположения безопасности. Каждая цель своей формулировкой должна описывать, что хотим достичь (состояние системы) Иными словами, она должно иметь форму утверждения, должна выполняться всегда, и отвечать на вопрос что?, также содержать описание актива.ущерба, который она «защищает». Предположения в схожей форме оговаривают некоторые внешние гарантии по отношению к системе, которые обеспечиваются за счет других систем. Помним правило, что для одной системы предположения – для другой цели, верно и обратное.

### Негативные сценарии

с помощью диаграммы последовательностей демонстрируем, как компрометация каждого из компонентов системы, определенных на этапе HLA, влияет на наши Цели Безопасности для каждого из сценариев. Иными словами, это диаграммы из вкладки  «Базовые сценарии + HLA», у которых поочередно «окрашиваем» компрометацией компоненты и демонстрируем влияние на другие компоненты и ЦБ. Снабжаем комментариями каждый такой сценарий. Обязательно рассмотреть негативные сценарии, нарушающие ЦБ.

### Политика Архитектуры

Наше финальное архитектурное решение, позволяющее при минимальных затратах обеспечить соблюдение всех ЦБ. С помощью диаграммы состояний путем расцвечивания, распределяем компоненты системы в рамках представления Data Flow Diagram (DFD) по трем категориям доменов (недоверенный, доверенный, повышающий). Помним подход – максимум недоверенных, минимум доверенных и повышающих. Также снабжаем компоненты оценкой сложности/стоимости помещения в доверенный или повышающий домен. Снабжаем таблицей с комментариями по каждому компоненту, почему он отнесен в тот или иной домен, а также обоснованием оценки сложности/стоимости.

## Критерий итогового решения

Помним, что наша задача, как Разработчиков, доказать Заказчику, что в рамках выбранной Политики Архитектуры, перечисленные ЦБ достигаются всегда с учетом Предположений Безопасности. В идеале, при описании Политики Архитектуры, описываются все сообщения между компонентами, запросы и ответы, чтобы при применении дополнительных способов изоляции компонентов и мониторов безопасности в рамках MILS/FLASK, можно было сразу определить их конфигурации.
